# akari-kit — 美術館の手筋ソルバーと難易度判定

ぬりかべ・ヤジリンで確立した形をそのまま適用した 3 種め。
**最初から段階モデル**(難易度の主軸を「要った読みの段階」にする)で書いてある。

## 構成

| ファイル | 役割 |
|---|---|
| `board.rs` | 盤面。光線 `rays()` と視界 `sight()` を持つ |
| `answer_model.rs` | 照明 / 非照明 / 未確定の 3 値。**照らされているかは持たない** |
| `answer_methods.rs` | 手筋が触る唯一の窓口。確定の記録もここで行う |
| `solution.rs` | 完成解のルール検証(ソルバーと独立に実装) |
| `search.rs` | 全探索。一意性の判定用 |
| `puzzlink.rs` | puzz.link URL の読み書き(`decode4Cell` 方式) |
| `solver.rs` | 段階エスカレーション + 仮置き |
| `difficulty.rs` | `段階 × LEVEL_SCALE + 手間` |

### 照らされているかを状態に持たない

照明を 1 つ置くと、その光の届く何マスもが「照らされた」に変わる。これを状態として
持つと、1 つの手筋が何十マスも書き換えることになり、**どの手筋が何を決めたかの記録が
壊れる**(難易度はその記録から計算する)。派生量として毎回数え直す方を選んだ。
盤面は高々数百マスなので、差分更新の複雑さを持ち込む理由がない。

## 手筋

| 段階 | 手筋 | 内容 |
|---|---|---|
| 1 | `clue` | 数字ぶん置けたら残りは非照明 / 置ける残りが数字ぶんちょうどなら全部照明 |
| 1 | `lamp_ray` | 照明の光の上には照明を置けない(相互照射禁) |
| 2 | `only_source` | 未照射のマスを照らせる場所が 1 つなら、そこが照明(救出) |
| 3 | `lamp_conflict` | そこに照明を置くとどこかが破綻するマスは非照明 |
| 4 | `clue_cases` | 数字まわりの置き方を全部並べ、どの置き方でも同じになるマスを確定 |
| 5 | `source_cases` | 「このマスを照らすのは誰か」で場合分けし、どの場合でも同じになるマスを確定 |

### カタログの「数字どうしの相互作用」は 1 つに畳んだ

ナナメ手筋・13 手筋・向かい合う 33・1 つおきの 11 は、どれも
**「そこに置くと隣の数字が足りなくなる」の言い換え**でしかない。
形を覚えて当てはめるのではなく、置いてみて破綻するかを直接見る方が短く、
取りこぼしもない。`lamp_conflict` 1 つで済んでいる。

逆向き(非照明にすると破綻するマスは照明)は新しい手筋にならない。
数字が足りなくなる場合は `clue` の飽和が、照らせなくなる場合は `only_source` が
先に同じ結論を出す。

### 数字まわりは全部並べられる

数字のまわりに照明をどう置くかは、たかだか 4 マスから選ぶだけなので**多くても 6 通り**。
`clue_cases` はそれを全部並べ、置いた照明の光まで押し込んでから
「他の数字が満たせるか」「照らせない白マスが出ないか」で篩い、
生き残った置き方すべてに共通するマスを確定させる。

`lamp_conflict` は照明を 1 つずつしか置いてみないので「2 つ置いたときだけ破綻する」
形を捉えられない。ぬりかべでいちばん効いた「シマの形の全列挙」の美術館版にあたり、
ここでも一番効いた(下表)。

移植元として調べた sdvx は 3 手筋(数字・照射・救出)しか持たないので、
`lamp_conflict` と `clue_cases` のぶん上回っている。

### カタログ E も 1 つに畳んだ

「ビーム」(かべが縦に連なると照明の置き方が 2 択に絞られ連鎖する)も
「回廊」(数字が組み合わさって白マスの並びが決まる)も、形は違うが理屈は同じで
**「照らし手が数通りしかない → どの場合でも同じところが決まる」**に尽きる。
`source_cases` はそれを直接回す。

仮置きとの違いは**場合分けの単位**。仮置きは全マスを照明/非照明で試すが、
こちらは「このマスを照らすのは誰か」という意味のある少数の場合だけを見る。
人が実際にやる読みに近く、そのぶん安い。照らし手が 6 通り以上ある広い場所は
まだ絞れていないので触らない。

### 計測で却下したもの

| 案 | 結果 |
|---|---|
| **予約**(カタログ D「アスピリンボックス」の一般形) | 未照射マス u を照らせる候補 C(u) の全部を見通す位置には置けない、という手筋。理屈は正しく **517 回発火する**が、段階の分布が 1 問も動かない。仮置きが既に同じところを拾っていた。実行時間だけ増えるので取り下げ |

## 使い方

```
cargo build --release --manifest-path rust/Cargo.toml
rust/target/release/akari solve "https://puzz.link/p?akari/10/10/hcscl.h.idn.i.cgcndg.h.ncs.h"
rust/target/release/akari solve "<問題>" --no-trial     # 仮置きを使わない
rust/target/release/akari solve "<問題>" --tier 2       # 段階 2 までの手筋だけ
rust/target/release/akari solve "<問題>" --depth 2      # 仮置きの入れ子を深くする
rust/target/release/akari answer "<問題>"               # 探索で正解を出す
rust/target/release/akari trace  "<問題>"               # 手筋を 1 つずつ回して経過を出す
python3 fetch_corpus.py                                 # puzsq から較正コーパスを取る
python3 measure.py --timeout 60 --jobs 8                # 解決率と段階の分布
python3 calibrate.py                                    # 難易度の較正
```

## 一意解でない問題の難易度は「-」

`solve` は `SOLUTIONS` を必ず出し、**一意でないと分かった問題だけ** `DP -` と表示する。
較正コーパスからも自動で外れる。

数え方に無駄がない。**手筋がすべて健全な演繹である以上、完解できたなら解は一意**
(どのマスも「他にありえない」から確定した)。だから探索が要るのは手が尽きたときだけ。

`SOLUTIONS` の値は 3 種類:

| 値 | 意味 | 難易度 |
|---|---|---|
| `1` | 一意 | 出す |
| `2+` | 複数あると分かった | **`-`** |
| `?` | ノード上限で数えきれなかった | 出す |

**`?` を伏せてはいけない。** 一度そう実装したところ、ぬりかべの手筋切れ問題が
163 問 → 4 問に激減した。大盤面ほど数えきれないので、**手が尽きた難問がまるごと
較正から消える**。「手筋では歯が立たなかった」は難しさの最も強い信号なので、
複数解の証拠がないまま捨てるのは間違い。数えきれなかったことは、複数あることの証拠ではない。

## 難易度較正(2026-08-05、puzsq 2,585 問)

| 指標 | 初回 | 手筋を足した | + 重みを較正 |
|---|---:|---:|---:|
| Spearman(人手評価, DP) | 0.689 | 0.728 | **0.748** |
| 完全一致 | 58.0% | 60.8% | **62.8%** |
| ±1 以内 | 97.9% | 98.5% | **98.6%** |
| 5-fold CV 一致率 | 56.8% | 59.8% | **62.3%** |

自由な当てはめのバンド閾値 1,000,726 / 3,001,150 / 4,004,408 / 6,045,824。
レーティング表示のアンカー(`difficulty.rs`)は 4.5 だけ段階 7 の開始点 6,000,000 に
構造固定してあり、そのときの完全一致は 61.6%(★5 の再現 14/28)。

### 手筋の重みはここでは効く(ぬりかべと逆)

ぬりかべでは重みを当てはめると過学習した(訓練 +2.6pt、CV −0.8pt)。
美術館では逆に、7 シードの CV が 59.79% → 61.90% に上がり、
**当てはめに使っていない別の 5 シードでも 59.75% → 62.13% と同じだけ上がった**。

理由は構造の違い。美術館は 9 割が手筋だけで解けるので仮置き系の項がほとんど 0 になり、
段階の中の順序が発火数だけで決まる。実際、仮置きの係数も残りマスの係数も、
走査すると CV が完全に平坦だった。

| 手筋 | 重み | |
|---|---:|---|
| 照明の光の上 | **0** | 10 万回以上発火するが、難易度ではなく盤面の広さを測っているだけ |
| 残りが数字ぶんちょうど | 2 | |
| 置くと照らせないマスが出る | 2 | |
| 数字まわりの場合分け | 2 | |
| 数字ぶん置けた | 8 | |
| 置くと数字が足りない | 12 | |
| 照らし手の場合分け | 24 | |
| そこしか照らせない | **64** | 突出。人が難しいと感じるのは数字ではなく「どこからも照らせない」を見つける読み |

参考: ぬりかべ 58.1%(CV 55.9%、Spearman 0.698)、
ヤジリン 58.2%(CV 59.7%、Spearman 0.737)。**3 種でいちばん良い。**

手筋を足して段階が割れると、難易度の一致率もそのまま上がる。
段階を主軸にした設計の裏づけになっている。

係数(`difficulty.rs`)はぬりかべの較正値をそのまま持ってきた暫定値で、
美術館では一度も走査していない。ここは伸びしろ。

## 速度

全 2,591 問で **70 秒**(8 並列)。効いた対処は 2 つ。

- **光線・視界・隣接マスを盤面の構築時に作り置きする。**
  手筋は 1 巡ごとに何万回も引くので、毎回 `Vec` を組み直していると
  大盤面で効かなくなる。これだけで時間切れが 14 問 → 1 問、全体で 4 分 → 2 分になった
- **`source_cases` が 1 巡で見るマスを 64 個までに絞る。**
  照らし手が少ない順に並べて上から試し、1 つでも確定したら戻る。
  絞れているマスほど確定が出やすいので、上位だけ見れば足りる。
  25x20 の盤面で 90 秒超 → 58 秒、時間切れが 1 問 → 0 問

### 部分集合での計測に注意

`MAX_CASES` を 5 → 12 に上げたとき、コーパスを 4 問に 1 問で間引いて計測して
「時間は増えない」と判断したが、**大盤面が薄まって時間切れの増加(6 問 → 14 問)を
見落とした**。速度に関わる変更は必ず全問で測ること。
