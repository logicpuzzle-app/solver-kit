# Yajilin Kit — ヤジリンのソルバーとジェネレータ（3言語実装）

ヤジリンのソルバーと自動生成器を、**TypeScript / Rust / Python** の3言語で実装したものです。
共通の設計から起こしており、同じシードを与えれば3言語ともバイト単位で同一の出力になります。

English: [README.md](README.md)

## 何をもとにしているか

**ソルバー**は `PuzzleTools/gridkit/frontend/src/puzzle/yajilin` の手筋ベースソルバーの移植です。
React への依存を取り除いたうえで、手筋を一つずつ忠実に再現しています。結果に影響する挙動の癖は、
勝手に直さず、該当箇所にコメントを添えてそのまま保存しました。

**ジェネレータ**は gridkit に存在せず、本プロジェクトで新規に設計したものです。構成は
[NPGenerator 2007 の4言語版](../../vendor/npgenerator) に倣い、決定的な乱数生成器を全言語で共有し、
共通 CLI・言語ごとの `verify.sh`・クロス言語ベンチマークを備えます。

## ソルバーが2つある理由

| | 手筋ソルバー | 制約エンジン |
|---|---|---|
| 実装 | `solver.ts`, `techniques/` | `engine.ts`, `search.ts` |
| モデル | 人間の解き方 | ルールが許すもの |
| 用途 | 難易度評価・解法の説明 | 生成・一意性の証明 |
| 完全性 | なし（途中で止まりうる） | あり（決定手続き） |

難易度は人間の推論についての性質なので、手筋ソルバーで測ります。一方で手筋ソルバーは完全ではなく、
手が尽きれば止まります。「この問題の解は一つだけ」のように**真であることが要求される**判定は、
すべて制約エンジンが担当します。

## CLI（3言語共通）

```
yajilin solve <problem>                 # 解答・難易度・盤面レンダリング
yajilin count <problem> [--limit N]     # 解の個数を数える（一意性の証明）
yajilin generate-loop [options]         # ループ先行方式で生成
yajilin generate-pattern [options]      # ヒント配置パターンから生成
yajilin bench [--count N] [--seed N]    # 生成・求解・計数の時間計測

<problem> はファイルパス、puzz.link URL、または "yajilin/W/H/body" 形式のコード。

  --seed N            乱数シード（既定 0）
  --size WxH          盤面サイズ（既定 10x10）
  --clues N           矢印ヒントの数
  --clue-ratio R      盤面に対するヒントの割合（既定 0.16）
  --attempts N        リトライ上限、0 で無制限（既定 100）
  --dp-min N/--dp-max N  難易度の範囲。外れた問題は作り直す
  --max-nodes N       探索ノード上限、0 で無制限（既定 200000）
  --symmetry S        none|rot2|rot4|mirror-h|mirror-v（パターンモード、既定 rot2）
  --pattern FILE      ヒント配置パターンを指定（パターンモード）
  --no-weaken         情報量の多い矢印方向のまま残す
  --no-reduce         冗長なヒントも削除しない（ループモード）
  --refine N          難易度を上げる山登りを N ラウンド行う（既定 0）
  --anneal N          貪欲な修復が行き詰まった際の焼きなましラウンド数（既定 1セルあたり8）
  --vary-clue-count   焼きなましにヒントの追加・削除を許す（難しくなるが約40%遅い）
  --black-bias N      セルを先に黒として試す確率（千分率、既定 850）
  --no-trial          仮置き（先読み）なしで解く
  --format F          url|code|text|grid（既定 grid）
  --out FILE          標準出力ではなくファイルへ書き出す
```

## 2つの生成モード

**`generate-loop` — ループが先。** 空盤面に対してランダムな正解（単一ループ＋黒マス）を1つ引き、
その黒マスの一部を矢印ヒントに昇格させます。昇格のたびに正解を引き直すのが要点です。セルがヒントとして
塞がれると、その隣接セルは黒に置けるようになるため、引き直した正解は**すでに置いたヒントに加えて**
以前と同程度の黒マスを持ちます。引き直さないと、ヒントを1つ置くごとに黒マスが1つ減り、最終的に
「盤面に黒が一つもない」というほとんど拘束のない問題へ流れていきます。

**`generate-pattern` — ヒント位置が先。** 対称パターン、または `--pattern` で与えた配置を使います。
それらのセルを塞いだうえで、周囲に正解を1つ引きます。

以降は両モード共通です。すべての矢印に方向を割り当て、一意解であることを要求し、そのうえで
**情報を削っていきます** — 一意性に不要なヒントを落とし、より情報量の少ない方向に差し替える、
という操作を一意性が保たれる限り続けます。

### エンジンが知っている規則

伝播は健全で安価な規則だけを適用します。どこまで確定できるかが生成の舵になるため、規則は好みではなく
**計測で採否を決めています**。

| 規則 | 判定 |
|---|---|
| 黒マスは4辺を消し、隣接セルをループへ押し出す | 中核 |
| ループセルの次数は2 | 中核 |
| 矢印の上下限（ceil(run/2) のパッキング上限つき） | 中核 |
| 線の断片は互いに到達可能でなければならない | 中核 |
| **グリッド線のパリティ** — ループは各グリッド線を偶数回横切る | **採用** |
| **小ループ禁止** — 断片を早期に閉じる辺を拒否する | **採用** |
| 矩形パリティ — 左上を固定した全矩形に同じ議論を適用 | 却下 |

パリティは二重の意味で価値がありました。同一シードでパターン12×12 の成功が 10/16 → 13/16 になり、
全体の実行が 2.6倍 速くなりました。

小ループ禁止は盤面により生成が 1.1〜2.5倍 速くなります（loop 12×12 で 123秒 → 49秒、成功は 8/8 のまま）。

矩形パリティも同じく健全でカバレッジは 38% → 42% に上がりますが、12×12 の生成は同じ成功率のまま
遅くなりました（149秒 → 182秒）。生成が必要としない推論に費用を払っている形です。

矢印パッキングの偶数ラン側の議論は**コードが不要**でした。ランは未確定セルしか含まないため、1つ確定すれば
ランが分割されて容量が再計算され、その時点で奇数ランが自動的にセルを確定させます。明示的なペア規則を
書いてみたところ、まさにこの理由でデッドコードでした。

### 試して効かなかったもの

6案をベンチで計測しましたが、いずれも上記の構成を上回りませんでした。再挑戦を防ぐため記録します。

| 案 | 結果 |
|---|---|
| 閾値受理の代わりに Late Acceptance Hill Climbing | 履歴長 10/50/200 いずれも差なし |
| カバレッジに「2つ目の解の見つけにくさ」を併せた目的関数 | あるシード帯では改善に見えたが独立帯で 13対13、40%遅い |
| 目的関数だけ意図的に弱いエンジンで測る | 差なし |
| 直近効いた近傍を優先する適応的重み付け | 計測可能な変化なし |
| 伝播で既に矛盾するヒントパターンを構築時に拒否 | 13/16 → 10/16。拒否が密集配置へ偏らせる |
| 偶数ランの明示的なペア規則 | デッドコード。ラン分割で既に導出される |

一方で**動いたのはベンチマーク自体**でした。出荷時の既定が `--attempts 100` なのにベンチは 20 で
回しており、運の悪いシードが「失敗」に化け、成功率をわずかに削って速度を取る候補がすべて不利に見えていました。
本来の既定では同じシードがすべて成功し、10×10 と 12×12 で 32/32、判定軸は時間に変わります。
小ループ禁止が却下から採用に転じたのはこのためです。

### 「ヒントがどれだけ確定させるか」を目的関数にした焼きなまし

一意性は yes/no の答えで、「まだ一意でない」しか分からない探索には登る勾配がありません。そこで貪欲な修復が
行き詰まったら、**素の伝播だけで正解のどれだけが確定するか**（`analysePropagation`）を目的関数とする
ヒント配置の局所探索に切り替えます。この値はヒントが効き始めるにつれて滑らかに上がるため探索に勾配を与え、
改善のたびに一意性を再判定します。

近傍は幾何的です。矢印は「どこに置かれているか」で見える範囲が決まるからです。

- ヒントを上下左右に1マス動かす
- 向きを変える
- 正解の黒マス上へ移す
- 未確定セルを最も多く見る向きに向ける
- 未確定セルの近くへ移す

`--vary-clue-count` を付けると、ヒントの**追加・削除**という2つの近傍が解禁され、phase 1 が盤面面積から
推測したヒント数を焼きなましが見直せるようになります。既定でオフなのは、計測結果が勝ちではなく取引だったからです
— 難易度が約50%上がる代わりに時間が35〜45%増え、成功率は同等かわずかに低下します。

受理判定は通常の `exp(-delta/T)` メトロポリス法ではなく**閾値受理**です。浮動小数の指数関数を使わないので
3言語がビット単位で一致します。停滞したら**再加熱**します。なお再加熱のたびに最良配置へ戻す案は試して
撤回しました。遅くなるだけで利得がなく、再加熱は多様化のために存在するのに、最良状態へ引き戻すと同じ盆地に
戻ってしまうからです。

パターンモードにも同じフォールバックを入れました（ヒント位置はパターンのものなので、向き変更の近傍のみ）。
以前は方向調整が行き詰まった時点で諦めており、それがパターンモードがどのサイズでも劣っていた理由でした。

これが大盤面を動かした要因で、12×12 は 5回中1回成功 → 8回中8回、10×10 は 20回中17回 → 12回中12回になりました。
候補の採否はすべて固定ベンチ `tools/bench-generation.mjs`（同じシード・サイズ・予算）で判定しており、
失敗の内訳は `tools/diagnose-size.mjs` が段階別に出します。

この設計はヤジリンの2つの性質から来ています。

- **矢印は黒マスしか数えない。** ある黒マス配置が2通りのループを許すなら、盤面のどこにどんなヒントを
  置いてもその2つを区別できません。生成器はこれを直接判定し（`countLoopRoutings`）、そうした正解は
  勝負にならない盤面として捨てます。
- **ヒントは削除できない。** ヒントはループが避けて通る障害物なので、消せば正解そのものが変わります。
  変えられるのは矢印の**向き**、そしてループモードでは矢印の**位置**です（ヒントを黒マスに戻し、
  別の黒マスをヒントに昇格させればよい）。`--refine` の山登りはこの2つを近傍操作として使います。

## 難易度

難易度スコア（DP）の主軸は **「その問題を解くのに要った読みの段階」** です。手間の合計
（手筋の発火数と仮置きの回数）は、同じ段階の中で順序をつけるためだけに使います。

`solve` はもともと段階的なカスケードで、安い段階が止まったときにだけ次の段階を呼びます。
だから「発火した最も深い段階」＝「その問題を解くのに最低限必要な手筋の集合」になります。
人間も同じ言い方で難しさを表します——「基本手筋だけ」「本数の勘定まで要る」「仮置きが要る」。

| 段階 | 内容 | puzsq 8,688問での該当 | ★1 | ★2 | ★3 | ★4 | ★5 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1 | 基本手筋 | 2,001 | 30% | 54% | 16% | 0% | 0% |
| 2 | 行・列の本数の勘定 | 367 | 6% | 47% | 46% | 1% | 0% |
| 3 | 切り口のパリティ | 237 | 4% | 49% | 46% | 1% | 0% |
| 4 | 線の本数の理論 | 85 | 2% | 36% | 54% | 7% | 0% |
| 5 | 仮置き | 5,713 | 1% | 16% | 56% | 26% | 1% |
| 6 | 解けなかった | 285 | 0% | 0% | 15% | 68% | 17% |

DP = `(段階 − 1) × 1,000,000 + 段階内のスコア`。

### v5 で変えたこと（2026-08-05）

ぬりかべ（`nurikabe-kit`）で確立した2つの考え方を移植しました。

1. **段階を主軸にする**（上記）
2. **「手筋だけで残ったマス数」を項に足す**（`PURE_UNDECIDED_COST = 10`）。
   手筋の発火数は難易度ではなく盤面の広さで決まってしまうが、
   「純粋な推論でどこまで進めたか」は申告と対応する（中央値 0 / 0 / 66 / 69 / 84）

puzsq コーパス 8,688問（一意解のみ）での効果:

| 指標 | v4 | v5 |
|---|---:|---:|
| Spearman（人手評価との順位相関） | 0.734 | **0.737** |
| 完全一致 | 59.5% | **59.9%** |
| 5-fold CV 一致率（7シード平均） | 58.73% | **59.69%** |
| 推定レーティングの加重絶対ずれ | 0.271 | **0.266** |

CV の範囲は v4 が 58.5〜58.9%、v5 が 59.3〜59.9% で**重なりません**。

素の努力量だけだと CV は 57.37% で、段階を主軸にすると 58.71% になります。その大半は
v4 の時点で `UNFINISHED_BASE` と `TECHNIQUE_FLOOR` が間接的に稼いでいたもので、
段階を明示すると +0.3pt、`pure_undecided` の項がさらに +0.6pt 乗ります。

### band（粗いラベル）

v5 から、生スコアではなく**推定レーティングから**決めます。生スコアには段階の項
（1段階＝100万点）が乗るので、段階1より上の問題が全部最上位バンドに入ってしまうためです。

| バンド | 推定レーティング |
|---|---|
| intro | < 1.50 |
| easy | < 1.75 |
| medium | < 2.52 |
| hard | < 2.79 |
| expert | < 3.35 |
| fiendish | ≥ 3.35 |

閾値は、v4 の生スコア閾値が puzsq コーパスで作っていた比率
（7.6 / 15.8 / 12.2 / 18.8 / 26.8 / 18.8 パーセント）を再現するように選んでいます。

### 注意: 生成の出力も変わります

`technique_work` に `pure_undecided` の項を足したので、生成の山登りの目的関数が変わります。
同じシードでも v4 とは違う問題が出ます（ゴールデンは再生成済み）。

`node --import tsx tools/calibrate-puzsq.mjs` で再現できます。

## ライブラリとしての利用

公開面は `typescript/src/index.ts` で、`npm run build` が型定義付きの `dist/` を出力します。
`PuzzleTools` の pnpm workspace に参加しているため、puzzle-kit は `workspace:*` で依存できます。

```ts
import { decodeUrl, runAll, difficulty, countSolutions, generateLoop, Rng } from "yajilin-kit";

const board = decodeUrl("yajilin/10/10/r31d32k22b31d23b31k33r12c40c13n");
runAll(board).status;                          // "completed"
countSolutions(board, 2).solutions.length;     // 1 — 仮定ではなく証明
generateLoop(new Rng(1), { cols: 10, rows: 10 });
```

puzzle-kit 側は `src/solver/adapters/yajilinKit.ts` で接続します。既存の `SolverAdapter` インタフェースを
実装し、id `yajilin-kit` で登録します。solver-kit ベースの既存 `yajilin` アダプタはそのまま残すので、
既にそれに依存している箇所の挙動は変わりません。新しい方は solver-kit 側に無いもの — 健全な一意性判定、
較正済みの難易度、生成 — を追加します。puzzle-kit で
`npx tsx src/solver/adapters/yajilinKit.smoke.ts` を実行すると往復の動作を確認できます。

## 検証

- **実問題での検証。** gridkit の1,308問すべてをデコードして解いています。手筋ソルバーは1,287問を
  完解し、完解した解はすべて独立したルール検証を通過、矛盾と誤判定した問題は0件です。制約エンジンは
  1,307問について一意性を証明し（1問はノード上限で打ち切り）、解なし・複数解の問題は見つかりませんでした。
- **乱数仕様の検証。** `tools/check-rng.mjs` が、高速化した24bit分割版 LCG と素朴な bigint 実装を
  シードごとに10万回比較します。
- **言語間の一致。** `testdata/expected/` にリファレンス出力を置き、各言語の `verify.sh` が `cmp` で
  バイト単位に比較します。Python は `PYTHON=pypy3 ./verify.sh` で PyPy 版も同じ検証を通します。
- **生成した問題**は返す前に必ず、独立したルール検証と一意性探索の両方を通します。
- **単体テスト**を3言語に用意しています（`npm test` / `cargo test` / `python3 -m unittest discover -s tests`）。
  バイト比較では位置を特定できない箇所 — 意図的に残した UnionFind の NaN 挙動、puzz.link コーデック、
  同じ公開アルゴリズムの独立実装と突き合わせる乱数、ルール検証、伝播規則 — を対象にしています。
  各言語の `verify.sh` がゴールデン比較の前にこれらを実行します。

## 性能

10×10 盤面、Apple Silicon での計測。生成の成功率は両モードとも20回中17回で、残りはリトライ上限に達して
失敗として報告されます（質の低い問題を返すことはありません）。

| | TypeScript (Node 22) | Rust (release) | CPython 3.12 | PyPy 7.3 |
|---|---|---|---|---|
| 5問生成 | 8.1 s | 3.8 s | 166 s | 69 s |
| 5問求解 | 0.84 s | 0.62 s | 14.4 s | 11.7 s |
| 5問の一意性証明 | 13 ms | 9 ms | 714 ms | 144 ms |

4つのランタイムすべてで平均難易度は同一です。速度は違っても、出てくる問題は同じという点がここの眼目です。
TypeScript の1問あたりでは、求解 59 ms（コーパス平均）、一意性証明 8 ms、生成 1.3 s（ループモード中央値）
または 0.6 s（パターンモード中央値）。

### Python と PyPy

Python 実装は無改変で PyPy でも動作し、`PYTHON=pypy3 ./verify.sh` で同一バイト出力を確認できます。
使う価値があるかは**実行時間の長さ次第**です。CPU時間・3回の最小値、PyPy 7.3.17 と CPython 3.12 の比較:

| ワークロード | CPython | PyPy | |
|---|---|---|---|
| `solve` 1問 | 0.22 s | 0.36 s | PyPy が 1.6倍 遅い |
| `count` 1問 | 0.21 s | 0.43 s | PyPy が 2.0倍 遅い |
| `generate-loop` 6×6 | 0.46 s | 1.61 s | PyPy が 3.5倍 遅い |
| `generate-pattern` 10×10 | 4.6 s | 6.7 s | PyPy が 1.5倍 遅い |
| `bench --count 3` | 59.1 s | 24.8 s | **PyPy が 2.4倍 速い** |

分かれ目は JIT のウォームアップです。単発コマンドはトレース費用を払うだけで回収できず、まとまった実行では
それを何倍にも償却できます。**1問だけなら CPython、大量生成なら PyPy** という使い分けになります。

Python 実装は両ランタイム向けにチューニングもしました。`IntEnum` メンバをプレーンな int 定数に置換、
`to_id`/`in_board` をホットな述語にインライン展開、`edge_around` の4方向ループ展開、束縛メソッドと
リスト属性のローカル退避。CPython で手筋ソルバーが1.4倍、パイプライン全体が1.2倍（70.4秒 → 59.1秒）
になり、PyPy にも効いています。
一方、CPython には効いたが **PyPy には有害だった**微最適化が2つあり（`list.extend` の `append` 分割、
`range(4)` の代わりにリテラルタプルを反復）、計測して撤回しました。それを検出したのが `tools/timeit.sh` です。

エンジンは3段階で最適化しました。いずれも出力が1バイトも変わらないことを確認済みです。ノードごとの状態複製を
トレイル方式の巻き戻しに置換、bigint 乱数を24bit分割演算に置換、盤面全走査の伝播をワークキュー駆動に置換。
これらにより20問生成が 86秒 → 17秒（**5.0倍**）になりました。連結性枝刈りはその後に追加したもので、
一部を返上して（17秒 → 28秒）成功率（20回中14回 → 17回）と 14×14 までの対応を得ています。

採用しなかった施策も1つ記録しておきます。ノード予算を使い切った際の探索リスタートです。空の15×15の探索は
通るようになりましたが、10×10 の生成が遅く・不安定になったため（25秒/17成功 → 38秒/16成功）撤回しました。

### 生成の現在地

`tools/bench-generation.mjs` で1セルあたり8シード、パリティ規則とパターンモードのフォールバック導入前との比較:

| | 導入前 | 導入後 |
|---|---|---|
| loop 10×10 | 8/8、中央値 915 ms | 8/8、322 ms |
| pattern 10×10 | 8/8、755 ms | 7/8、864 ms |
| loop 12×12 | 8/8、6.8 s | 8/8、17.8 s |
| pattern 12×12 | **4/8**、9.9 s | **6/8**、6.6 s |
| 全体 | 28/32、331 s | 29/32、216 s |

8シードはばらつくため、採否は動いたセルに絞った16シードの計測で決めています。パターン12×12 は
パリティにより 10/16 → 13/16 になり、同じ作業量が 326秒 → 127秒 になりました。

## 既知の制限

- **ループモードは 15×15 まで到達、パターンモードは届きません。** ループモードは 15×15 を安定して生成できます
  （4/4 シード、すべて有効・一意）が、1問あたり3〜20分と遅く、10×10 の約1秒とは桁が違います。
  パターンモードは 12×12 までが実用範囲です。ヒント位置がパターンで固定されるため、ループモードのように
  一意になるまでヒントを足していくことができません。
- **15×15 の壁の大半は試行回数の使い方でした。** このサイズでは抽選した対称パターンの4分の3が解無しで、
  そのたびに「一意にできなかった問題」のための試行枠を1つ消費していました。これを無料で引き直すようにしたことが、
  サイズを開いた最大の変更です。
- **ループモードの穴はすべて黒マス由来**のため、ヒントセル同士が直交隣接することがありません。手作りの
  問題にはこの制約はありません。パターンモードはヒント位置を先に決めるため、この制限を受けません。
- **手筋ソルバーはコーパス1,308問のうち21問を解ききれません。** これらはモデル化していない手筋を要するもので、
  制約エンジンでは解けます。

## ライセンスと出自

ソルバーは同リポジトリ内の gridkit に由来します。ジェネレータ・制約エンジン・各言語移植は新規実装です。
乱数生成器は `java.util.Random` として文書化されているアルゴリズムを、その仕様から再実装したものです。
